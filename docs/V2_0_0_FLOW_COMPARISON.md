# 2.0.0 与当前版本：过帧、Seed 和推进数流程对比

对比日期：2026-10-29。

基准是本地 Git 标签 `v2.0.0`，提交 `fa3f6550c872efa77083c901fc9ce64e6659b43e`。当前代码固定到 `659131de433b3c2f1cf0af0882765aa4589633ae`，即 3.4.4 基础上包含近期尚未发布的修复。已发布 3.4.4 是 `61802f4`；报告会明确区分近期本地修复。

**结论：Seed 反推和两种推进计时器的核心计算没有发生版本变化；过帧后的部分分支、校正搜索、失败初始化、默认脚本及执行后端有实质变化。失败恢复机制的变化值得优先验证，但尚不能确定它是现场持续测种失败的原因。**

## 1. 过帧结束后的处理

### 普通过帧：分支规则相同

两个版本都按本次请求的过帧量判断：

```text
本次过帧量 > 重测阈值：完整重新测 Seed → 搜索新目标
本次过帧量 ≤ 重测阈值：用原 Seed 校正当前推进位置 → 继续检查原目标
```

默认重测阈值在两版均为 900,000。当前版本增加了可配置入口。

实际对照 899,999、900,000、900,001 及用户日志中的 104,523,047：分支结果相同。104,523,047 在两版都会进入完整测种，**不会在这个分支把“旧 Seed + 请求过帧量”直接当作真实新 Seed**。

位置：旧版 `runner.py:371` / 当前 [decide_after_advance_script](D:/codex_project/auto_bdsp_rng/src/auto_bdsp_rng/automation/auto_rng/runner.py:438)。

### 已执行过场脚本后：处理不同

旧版在“已过场、已经错过目标、后续目标又超过重测阈值”的特定条件下才直接换轮；其余部分情况仍可再次大过帧并完整测 Seed。

当前对 `after_exit_reseed` / `_exit_reseed_done` 增加限制：过场后如果还需超过阈值的大过帧，直接运行测种脚本开始下一轮，不在该状态原地完整测 Seed。过帧结束处也有同类保护。

对照执行中设置“已过场、本次过帧 104,523,047”：旧版下一阶段为完整捕获 Seed，当前为运行测种脚本。

这条差异要求“已过场”标记成立。用户贴出的“过帧完成 → 正在重新测种”日志对应完整测种分支，不能仅用过场保护解释那次失败。

位置：当前 [过帧决策](D:/codex_project/auto_bdsp_rng/src/auto_bdsp_rng/automation/auto_rng/runner.py:940)、[过帧脚本结束处理](D:/codex_project/auto_bdsp_rng/src/auto_bdsp_rng/automation/auto_rng/runner.py:1000)。

### 完整测种成功后的清理更彻底

旧版接受新 Seed 后重置计时器，但没有在该入口统一清理旧目标、请求过帧量和全部候选。

当前通过 `_adopt_captured_seed` 清理旧目标、请求推进数、候选、过场标记等，再以新的 Seed 和当前推进 0 开始搜索。普通定点初始推进 0 的口径没有变化；御三家全自动另有专用初始推进 1，不适用于这次普通定点案例。

位置：当前 [接受完整测种结果](D:/codex_project/auto_bdsp_rng/src/auto_bdsp_rng/automation/auto_rng/runner.py:692)。

实际调用两个版本的反推函数，分别使用 NPC 0、1、2，在普通位置和跳过 104,523,047 次后的状态生成观测：6 组有效观测均返回完全相同的状态，并与独立 RNG 模型一致。再分别人为改动一位眨眼类型，两版都由同类断言拒绝该输入。

错误观测是人为构造的，用于确认两个版本对相同输入的行为；它不是用户现场故障的复现。

### 求解后的耗时补偿也沿用旧版

两个版本都使用：

```python
elapsed_seconds = max(0, round(time.perf_counter() - observation.offset_time))
elapsed_advances = elapsed_seconds * (npc + 1)
state = advance_seed_state(state, elapsed_advances).state
```

`offset_time` 来自末次采集眨眼的参考时点，补偿的是采集结束至取得结果的耗时，不是整个九小时过帧时长。`advance_seed_state` 的函数实现也完全一致。

当前调整了预览恢复的顺序：自动测种在采集结束的 `finally` 恢复预览，再求解及补偿；旧版在取得 Seed 和 `measured_at` 后恢复预览。此处存在调度边界变化，补偿表达式本身相同。

另有一个两版共有的计时口径：这里按整秒补偿，普通计时器按每 1.018 秒推进一次。例如耗时 100 秒，这里补偿 100 次，按 1.018 秒周期换算约为 98 次。长求解耗时下值得单独校准这一近似；它不是本轮版本对比发现的新回归，而且发生在求解成功之后，不能直接解释求解器内部的校验断言失败。

当前共用入口：[求解和耗时推进](D:/codex_project/auto_bdsp_rng/src/auto_bdsp_rng/ui/main_window.py:10605)。

## 3. Advance 的计算

### 普通活帧计时：整个类完全一致

`ProjectXsAdvanceCounter` 的源码在两版完全一致：

```text
每个 tick = 1.018 秒
每个 tick 增加 max(1, npc + 1) 次推进
从测得状态的 measured_at 开始计时
```

对 NPC 0、1、2，分别在 0、0.5、1.017、1.018、60、3,600、34,690.127 秒采样，21 次对照的推进数和下一次触发时刻完全一致。最后一项是用户长脚本的耗时量级，但这是虚拟时间对照，没有实机等待。

翻图鉴的快速推进由脚本执行完成后重新测种或校正来确定位置；不能把普通站立计时的 1.018 秒周期直接当作图鉴快进速度。

位置：旧版 `runner.py:38` / 当前 [普通推进计时器](D:/codex_project/auto_bdsp_rng/src/auto_bdsp_rng/automation/auto_rng/runner.py:58)。

### 过场 Timeline：整个类也完全一致

`ProjectXsTimelineAdvanceCounter` 与创建、重置计时器的方法完全一致，仍使用原有 1.017 秒玩家事件、宝可梦事件间隔及 Advance Delay 参数。

两套 NPC/延迟参数、12 个时间采样点的推进数、内部 RNG 状态和事件队列均一致。

位置：旧版 `runner.py:95` / 当前 [过场推进计时器](D:/codex_project/auto_bdsp_rng/src/auto_bdsp_rng/automation/auto_rng/runner.py:115)。

### 目标启动点：固定模式相同，新增模式有差异

旧版使用固定 delay，撞闪脚本必须声明 `_闪帧`：

```text
脚本启动 Adv = 目标 Adv − delay − _闪帧
请求过帧量 = 脚本启动 Adv − 当前 Adv
```

当前对这种脚本保留同一公式；42 组固定 delay、闪帧和边界位置的对照结果一致。变化在于：

1. 当前可按轮次策略解析 delay，并在该轮冻结，也可将实际使用的 delay 绑定到候选；若仍选择固定策略，数值相同。
2. 没有 `_闪帧` 的脚本现在允许由软件等待到 `目标 Adv − delay`，旧版会因缺少参数而拒绝。零距离启动点的处理也有专用分支。
3. 当前增加 `(启动点 − 当前 Adv) % (npc + 1) == 0` 的可达性检查，排除普通活帧步长无法正好到达的候选；旧版没有这项筛选。

位置：[启动点决策](D:/codex_project/auto_bdsp_rng/src/auto_bdsp_rng/automation/auto_rng/runner.py:265)、[可达性检查](D:/codex_project/auto_bdsp_rng/src/auto_bdsp_rng/automation/auto_rng/runner.py:471)、[轮次 delay](D:/codex_project/auto_bdsp_rng/src/auto_bdsp_rng/automation/auto_rng/runner.py:1808)。

## 4. 校正位置的变化

校正与完整反推 Seed 是两个入口。两版校正后都保留原始基准 Seed，只更新 `current_advances`；抗干扰流程另保存 `timing_seed` 给 Timeline 使用。这一口径没有变化。

| 项目 | 2.0.0 | 当前 |
| --- | --- | --- |
| 执行方式 | Python Project_Xs | 优先 C++ 原生校正，不可用时回退 Python |
| 普通校正提示窗口 | 下限 `hint − 10,000`，上限沿用全局搜索上限 | 先搜 `hint − 10,000 .. hint + 20,000`，未命中再扩大 |
| 无提示的抗干扰校正 | 沿用全局搜索上限 | 默认最多 100,000 的窗口 |
| 提示后的抗干扰回退 | 无当前的分段回退 | 补充提示两侧的有界窗口 |
| 过场抗干扰校正 | 全局搜索上限，至少 100,000 | 固定 0..1,000,000 |
| 普通校正失败策略 | 固定尝试 2 次，失败换轮 | 次数可配置，可选择完整测种补救 |
| 过场校正失败 | 尝试 2 次后换轮 | 仍固定最多 2 次后换轮 |

原生与 Python 的原有 6 项差分测试全部通过，包括 250,000、500,000、900,000 的远位置及抗干扰匹配。另补做 NPC 0、1、2 的各采样相位对照，6 组推进位置和返回状态一致。这支持所测数据上的计算等价，不等于穷尽所有输入。

搜索范围变化可能改变“能否命中、需要多久、是否进入补救或换轮”，需要按实际运行参数判断。但用户首次失败日志明确走完整重新测 Seed，不能直接把原生校正窗口的变化当成该次完整反推失败的原因。

## 5. 失败恢复是重点行为差异

### 2.0.0：失败后强制启用脚本初始化

旧版 `_restart_from_seed_script` 设置 `_need_init_reset = True`。下一轮读入测种脚本时，将 `$初始化 = 0` 临时替换成 `$初始化 = 1`。

旧默认脚本具有对应条件块，包含双 HOME。因此，使用该默认脚本时，失败换轮会强制执行这段初始化，不依赖 OCR 是否识别到缩放提示。

### 当前：按识别结果恢复

`24b6640`（2026-08-05）删除上述标记、临时替换和默认脚本初始化块，改为后续轮次先调用 `recover_zoom_mode`。

当前服务要求前后两次画面都识别到缩放/锁定提示才发双 HOME，之后再次检查是否已经恢复。任一次未识别到提示时直接继续测种脚本。手动重新从测种脚本开始的新任务首轮不执行这项额外检查。

对照代码执行已确认：

| 场景 | 2.0.0 | 当前 |
| --- | --- | --- |
| 失败换轮，使用各自默认脚本 | 发出含 `$初始化 = 1` 的测种脚本 | 调用识别服务；默认脚本没有初始化条件块 |
| 当前识别服务返回否 | 旧版不依赖此判断 | 不发专用恢复脚本，继续测种脚本 |
| 将旧测种脚本交给当前 Runner | 旧 Runner 会临时启用初始化 | 当前 Runner 不再改 `$初始化 = 0`，只依赖识别服务 |

这里替换了识别服务返回值以观察分支，没有测试现场 OCR 的准确率或实机 HOME 效果。

**这项变化与“某次失败后自动恢复持续失败，重新开始却能成功”的恢复边界更相关，值得优先验证；它仍不能单独解释第一次完整求解为什么失败。** 停止后的截图不能证明重试前的识别一定漏判或误判，也不足以认定根因。

位置：旧版 `runner.py:693,1284` / 当前 [测种脚本前处理](D:/codex_project/auto_bdsp_rng/src/auto_bdsp_rng/automation/auto_rng/runner.py:898)、[缩放恢复服务](D:/codex_project/auto_bdsp_rng/src/auto_bdsp_rng/automation/auto_rng/zoom_recovery.py:40)。

### 连续五次保护与轮数越限

连续 5 次完整测种失败就停止的策略，2.0.0 已存在。失败换轮超过设定轮数的问题也不是新版本才出现。

用同一条“循环 10 次、前 6 轮成功、第 7 轮长过帧后注入测种失败”的流程对照：旧版启动到第 11 轮并由五次失败保护停止；当前启动到第 10 轮后停止。这里当前的轮数上限检查来自近期本地提交 `5325398`，尚不在已发布 3.4.4 中。

### 脚本执行后端发生过替换

2.0.0 自动流程经 EasyCon Bridge 或 CLI 执行；`0660f65`（2026-08-26）后接入原生 EasyCon 运行时和共享视频源。当前自动流程使用原生后端，控制器执行、脚本完成/停止、资源保留和释放的代码与旧版不同。

`639c18f` 后将“结束当前脚本”和“取消整次任务”分离。旧版停止脚本会设置捕捉取消标记，之后捕捉入口再清除；当前整次任务取消另有独立对象。不能将它概括成两个版本使用完全相同的执行环境。

这部分可能影响实机动作和恢复时序；本次没有比较两种后端在相同硬件上的长时按键波形，也没有据此认定后端存在故障。

## 对当前问题的判断

1. **没有找到“新版更换了 Seed 反推或普通推进计时公式”的证据。** 同输入的实际计算结果与旧版一致。
2. **明确找到了失败初始化、过场分支、校正搜索、脚本和后端的行为变化。** 其中失败初始化替换最值得针对后续恢复不良做受控对照。
3. **“第一次失败”和“之后一直恢复不了”需要分别定位。** 优先保留首个完整求解的原始异常与输入，再核对失败换轮前是否识别、执行和确认了正确的恢复动作。
4. 本次为版本对比与验证，没有据此改动生产流程或回退某个版本。恢复路径是否需要调整，仍应由现场诊断和实机对照决定。
